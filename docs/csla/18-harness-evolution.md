# Harness 进化理论（ECH-S v1.1）

> 版本：v1.1 · 2026-10-10
> 上一版：《Stylotrace × CSLA — 冻结模型、进化 Harness v1.0》
> 本文只写**判定规则**，不写愿景。每条规则都要能在一行代码或一个测试里被违反。

v1.0 的骨架是对的：运行时只管用已批准的 Harness，进化系统只管提案→评估→发布，两个平面用版本号连接。
但有五处在实施时会塌掉，这一版逐条修。

---

## 1. 权限论：自动循环的权限由**写入范围**决定

v1.0 把 shadow / canary / 灰度发布当成通用发布链（§9.4 七步）。这是从服务端产品搬过来的。

**本产品的实际情况**：Harness 存在**用户自己的工作区**（`protocol/harness/`）。
一个只往自己工作区写东西的循环，**在构造上就不可能影响别人**。

推论有三条：

1. 运行时进化循环**不需要灰度**——它的作用域本来就是一个人。给一个人的改动做金丝雀，是把企业级流程套在个人工具上，结果是永远发不出去。
2. 真正影响所有使用者的东西（提示词库、候选库、评估器定义、安全规则）**都在代码里**。改它们的唯一途径是改代码、发版本、由人评审。这不是"审批流程"，这是**代码发布**。
3. 所以 v1.0 §9.4 那条七步链，**前五步属于运行时循环（可以轻），后两步属于代码发布（必须重）**——把它们串成一条链是分类错误。

这条规则在代码里的对应物是 `harness.js` 的 `AUTHORITY`，以及"冻结区靠白名单执法"这个事实：
白名单之外的一切，循环**连碰都碰不到**。

## 2. 可优化性前提：可调参数必须**有张力**

v1.0 给了一份"允许进化的对象"清单（§4 十条），默认清单上的东西就是可调的。

**这是错的。** 一个参数可调，当且仅当：

> 存在两组状态，让这个参数往两个方向都能胜出。

否则它不是参数，是**装饰品**——写进配置很好看，改了没有任何效果。

2026-10-10 实测：本项目 13 个可进化键里，**只有 1 个真的能改变行为**。
原因是候选库里所有候选的回答成本都等于 1，而且"信息增益高"的候选恰好"侵入性低"，
两个排序完全一致——λ 和 μ 无论怎么调，argmax 都不变。

所以 v1.1 立一条设计规则：

> **每加一个可调权重，必须同时给出让它往两个方向都可能胜出的状态或候选；
> 并且必须有一条探针能把这件事机械地验证出来。**

这条规则不接受"理论上应该有用"。`elicit.js` 的 `weightLiveness()` 就是探针，
`stylotrace harness` 每次都会打印四个权重是"活的"还是"装饰品"。
为了让 λ 和 μ 真的活起来，候选库里补进了"高价值但要作者付出更多、也更私密"的问题
（`own-story` / `personal-fact`）与"低价值但零负担"的问题（`common-view`）。

## 3. 验收门按**影响范围**分级

v1.0 只定义了冻结区（不许改）和非冻结区（可改），中间没有分级。一套门走天下会导致两种对称的失败：

- 给个人级改动上企业级门 → 永远发不出去，进化循环变成摆设；
- 给全局级改动用个人级门 → 悄悄污染所有人。

v1.1 定义三层，门的强度与影响面成正比：

| 层 | 例子 | 谁能改 | 验收 |
|---|---|---|---|
| **W 工作区层** | 提问权重、检索条数、候选数 | 运行时循环可自动发布 | 见 §4–§6 的门 |
| **C 代码层** | 提示词模板、候选库、算子实现 | 只能由人改代码发版本 | 代码评审 + 全量回归 |
| **F 冻结层** | 状态结构契约、权限、事件完整性、安全不变量、**评估器**、**留出集** | 谁都不能 | — |

关键在第 W 层的留出集**测什么**：它测的是**同一位作者、未参与提案的后续任务**，
不是"别的用户"。这一点必须写在门上，否则会误以为自己拿到了跨用户泛化证据。

## 4. 成本必须进门槛

v1.0 把 Cost 列为指标（§11），但没有进发布门。

在写作场景里，"多想一轮"几乎总能提升某些质量指标。没有成本项的门，等于**奖励无限思考**——
而这是一个用户自己付费的产品，多花的是他的钱。

所以门里必须有：`costDelta ≤ 0.25`。靠多花 token 换来的"提升"不算提升。

## 5. 评估器阶梯：机械优先，模型评审不得单独作证

v1.0 列了十几个指标名（Intent Fidelity / Author Fit / …），但没说怎么测。

这不是细节，是成败点：**优化器一定会朝评估器喜欢的方向走**。
如果评估器是另一个模型，优化器就会去讨好那个模型——而这正是本项目早就明确拒绝的方向
（不做 AI 判定器，见 CADENCE 的三条"不做"）。

所以 v1.1 规定一个**固定优先级**，能往上走就不许往下走：

```
mechanical   >  recomputable  >  blind_human  >  llm_judge
确定性可判定    可复算、同输入同输出   作者盲选        模型评审
```

并且：**`llm_judge` 不得作为唯一证据**，必须在结果里带 `corroboratedBy` 才能过门。

原则一句话：**评估器必须比被优化的对象更硬。**

## 6. 样本量下限是**拒绝条件**，不是目标

v1.0 的假设 B 要求"优化能在未参与优化的任务上带来可重复改善"。
个人写作的轨迹量是几十条量级，在这个量级上做 GEPA 一类的选择会直接过拟合。

所以 `minSampleSize = 8` 的含义不是"至少跑 8 个"，而是：

> **少于 8 个时，观测到的提升与噪声不可区分，因此系统拒绝发布。**

**拒绝是功能，不是失败。** 一个只会说"进步了"的进化系统没有价值。

## 7. 由以上得到 ECH-S v1.1 判定链

```
真实运行产生轨迹（事件已带 harness_version）
        ↓
故障分类（intent_drift / redundant_question / overclaim …）
        ↓
定向提案（只改被归因的部件；碰冻结区 → 直接拒收并留负证据）
        ↓
可优化性检查（这个参数是活的吗？死的就驳回提案）
        ↓
评估（按阶梯取证据：机械 > 可复算 > 盲选 > 模型评审）
        ↓
过门（配对 + 留出集 + 样本≥8 + 提升≥0.02 + 零回归 + 成本≤0.25）
        ↓
发布（版本叠加） 或 拒绝 / 回滚
        ↓
≤ 代码层 / 冻结层：不在本循环权限内，属代码发布
```

## 8. 可证伪假设（修正版）

**假设 A**：在相同基础模型、相近 token 预算下，CSLA 的主动澄清与状态化简报能改善作者意图保真度。

**假设 B**：在固定评估与安全条件下，通过真实反馈优化 Harness，
能在**未参与优化的任务**上带来可重复改善，**且不增加成本**。

两处修正：一是把"相近资源预算"写成硬条件而不是描述（§4）；
二是明确"未参与优化的任务"指的是**这位作者的后续任务**（§3），不是跨用户泛化。

如果 B3 不优于 B2 → 假设 A 未获支持；
如果新版本只改善提案样例、不能迁移到留出任务 → 假设 B 不成立。

## 10. 这一版仍然没有解决的

- **跨用户泛化完全没测**。现在所有证据都来自单作者，假设 B 只在个人层成立。
- **"张力"目前只有提问权重一处落实**。其余 9 个可进化键（检索条数、候选数、动作权重等）还没有探针，
  很可能同样是装饰品。
- **成本只是"不许增加"，没有"必须更省"**。真正的改进应该是同等质量下更省。
- **故障分类到提案之间仍是人在搭桥**，自动反思回路（v1.0 的 Phase E）没做。
- **评估器本身没有被验证**。阶梯规定了优先级，但没证明 `mechanical` 那一档的判别力。
